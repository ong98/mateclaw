# 工具回执保留与恢复

领取、创建、提交等操作的成功回执是后续办理依据。上下文裁剪只影响模型看到的正文，不能要求重新执行有状态操作找回旧结果。

## 运行机制

- `ActionNode.completeBatch` 从已完成事件保存原文，按工具调用标识建立本轮索引。原文不可覆盖，索引随批次更新；最近 24 条调用的正文限制不影响索引内容。
- 执行事实提示始终提供 `receiptIndexPath`。模型通过既有 `read_file` 读取索引，再根据 `resultRef` 读取原文。参数仅存脱敏预览，结果摘要不代替完整原文。
- 不超过 512 字符的旧回执直接保留；长回执在年龄压缩及预算裁剪前保存为文件引用。落盘失败时保留原文，并防止后续软裁剪、清理和摘要预处理将未保存的业务回执丢弃。
- 读取工具沿用原始文件入口，避免读取结果再落盘的递归；`returnDirect` 的正文和调用参数不进入恢复索引。
- 进行中或受阻步骤的 `progress_update.note` 展示最多 512 字符，记录实际返回标识、请求标识、已完成项和下一步。调用成功不等于整个办理步骤完成。
- 用户显式发起新一轮操作时建立独立台账，正常执行；不缓存同参数的业务调用，不拦截新的授权操作。

恢复路径复用 `ToolResultStorage` 的目录、成员隔离、会话删除和保留期策略，不新增接口、表、后台任务或质检业务状态。

## 开发验证

`ActionReceiptRecoveryIntegrationTest` 使用真实执行节点、执行器、回执文件和 `read_file`，业务服务使用计数回调：领取一次 → 连续取证 30 次 → 裁剪历史 → 读取索引和原文 → 两项各提交一次。随后同一会话显式新一轮领取仍执行且使用独立索引。补充测试覆盖不可覆盖原文、索引更新、会话隔离、存储失败、短回执、成员目录和直接返回边界。

这些是研发本地回归，不代表真实模型或生产质检服务已完成端到端验收。真实模型仍需按照回执恢复提示和技能要求推进业务。

## 后续优化建议（2026-10-14 保留）

当前方案采用短回执保留、原文外置、按需恢复和进度摘要，已经补齐原回执的恢复入口。后续优化的核心是让未完成办理信息直接可见，并建立可验证的推进条件。以下建议暂存为后续迭代依据，先重启基础修复版本，由用户验证真实案件质检效果。

| 维度 | 当前优势 | 当前不足 |
| --- | --- | --- |
| 数据完整性 | 普通业务回执保存原文，摘要遗漏后可恢复 | 原文存在不保证模型及时找到并使用 |
| 上下文成本 | 长结果使用文件引用，减少重复发送全文 | 恢复通常需要先读索引再读原文，增加调用和等待 |
| 办理衔接 | 保留标识、请求 ID 和下一步 | 备注是自由文本，推进仍依赖模型，缺少可验证的完成条件 |
| 通用性 | 不依赖案件质检字段 | 工具成功不能直接证明业务步骤完成 |
| 工程成本 | 复用现有存储和账本 | 索引随每批完整重写，大规模调用时有额外读写开销 |

容量规则如 512 字符、最近 24 条调用不能直接代表业务重要性。未完成步骤引用的早期回执，应优先于普通近期查询结果保留。

### 与常见上下文管理模式的取舍

| 模式 | 适用用途 | 局限与使用边界 |
| --- | --- | --- |
| 滑动窗口 | 保留近期交互，控制上下文成本 | 会遗忘早期关键事实，不单独承担办理状态保存 |
| 滚动或分层摘要 | 保留目标、决策、过程和交接 | 摘要有损，不能作为原始业务回执的替代 |
| 原文归档与按需读取 | 精确保留工具回执和证据 | 需要正确定位原文，恢复有调用开销 |
| 检索式记忆或 RAG | 从大量规范和知识资料查找相关内容 | 业务标识和提交状态需要精确定位，不能依赖语义近似命中 |
| 结构化状态与执行检查点 | 记录未完成项，支持中断续办 | 需要明确状态与完成条件，优先复用已有账本 |
| 提示词缓存 | 降低重复前缀的成本和延迟 | 不增加有效上下文，不保证业务办理完成 |

### 迭代顺序与验收依据

1. **结构化当前办理状态。** 从真实领取和提交回执自动构建当前批次、未提交明细、已完成项、请求标识、下一步和证据引用。由程序生成每轮可见的简短快照，未完成项持续保留，长证据外置，解释过程保留在摘要中。
2. **批次推进条件。** 对声明逐批办理的质检技能，只有本批必需项全部提交成功才可推进下一批；不满足时指出具体未完成项。规则在技能或工作流层声明，通用运行时负责执行约束，允许并行领取的业务遵循自己的流程。
3. **跨轮续办检查点。** 达到迭代上限或中断后，复用持久化账本恢复未完成批次、已提交结果、剩余动作和回执引用。明确区分继续上一轮与显式开始新一轮，避免重复执行已完成操作或跳过新授权操作。
4. **按当前步骤选择上下文。** 提交阶段优先提供领取明细、结论和提交契约；图片分析阶段提供对应证据与适用规范。按未完成步骤的引用关系保留关键回执，优先按调用或业务标识精确定位。规范和工具说明在同一任务内保留版本或来源后复用，实时状态按需重新查询。
5. **真实模型效率验证。** 通过真实模型和模拟业务服务记录未提交时重复领取次数、必需结果提交完整率、压缩后恢复调用数、重复规范读取次数、总耗时和 token 消耗，再根据真实案件复跑结果决定后续实施顺序。

优先实施顺序为结构化办理状态、批次推进条件、跨轮续办检查点。新增接口、表、后台任务或恢复分支须有实际场景支撑，并在实施前核对现有账本和工作流是否已经提供相应能力。
